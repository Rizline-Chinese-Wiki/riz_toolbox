# Plan: foundation-expansion

## Overview

RizToolbox 的职责是 Rizline PC Mod 的公共底层。项目维护者负责运行时接入、稳定 SDK、游戏版本适配、插件共存和验证；功能作者在其上制作查分、皮肤、练习、谱面工具等。下一阶段以公共能力的覆盖度推进，验收样例用于证明接口，不把业务 Mod 当作底层交付。

本计划承接 [0.2 原始计划](../compatibility-foundation/README.md)，以现有六个工程增量演进。采用已有五份标准文档结构；用户已明确角色和目标，不需要再次选择技术栈或文档档次。文中新增接口名称是设计方向，只有通过实现与验收后才进入正式 SDK 文档。

## Goals

- 覆盖四类兼容性：游戏版本适配、插件/API 版本兼容、插件私有依赖共存、对游戏同一目标修改时的协调。
- 让插件通过稳定身份、普通数据和可撤销句柄使用游戏；游戏地址、Unity 对象和 IL2CPP ABI 细节集中在适配器与运行时。
- 覆盖 Mod 常见接入面：生命周期、游戏状态、判定、时钟、资源、界面、输入、音频、谱面、设置与本地数据。
- 同时提供易用的高层服务和经过签名验证的高级扩展机制；新增游戏接入点应能登记为独立适配模块，避免每次都扩大 Loader。
- 所有修改都有所有者、冲突策略、有效期、撤销规则和诊断；每项能力标注版本支持与验证范围。
- 实现代理按小任务交付代码与证据，维护者主要评审边界、契约和架构，不必开发业务 Mod。

## Non-Goals

- 不把完整查分产品、皮肤商店、练习界面、谱面编辑器、账号系统或在线工坊后端纳入底层交付。
- 不承诺任意游戏版本、任意原生函数签名、任意第三方注入器自动兼容，也不把依赖隔离宣称为进程级安全隔离。
- 本轮不以脚本语言宿主、多进程 IPC、无需重启的 DLL 热替换或通用二进制改写器作为发布前提；这些可以后续通过现有能力边界扩展。

## Coverage baseline

状态含义：**已验范围**只覆盖已有证据；**部分**表示范围不全；**待复测**表示代码或修复存在但真实流程未完成；**待实现**表示尚未交付。

| 公共能力 | 2026-10-19 基线 | 下一阶段交付 | 任务 |
|---|---|---|---|

| 开局、结算与局标识 | 场景和失败结算已实测；开局漏报待复测 | 完整单局状态机、重试/退出/暂停语义 | B01、B09 |

| 插件包和依赖 | 独立包与私有 DLL 隔离已验 | 可选依赖、冲突声明、持久启用意愿、迁移 | B04 |

## Milestones

| 顺序 | 任务 | 可验收成果 | 出口条件 |
|---|---|---|---|
| P0 收口当前缺陷 | B01–B02 | 可信的单局事件和原生读写基础 | 同一 RunId 开局/结束成对；失败、正常结束、重试、退出分别有证据 |
| P1 稳定公共骨架 | B03–B06、B18 基础 | SDK、包、作用域、模块与诊断协议 | 两个独立探针使用同一 SDK；能力消失后清理，恢复后按意愿启用 |
| P2 共用接入机制 | B07–B09、B12 | Hook、修改协调、生命周期、对象定位 | 同一目标两个插件共存，撤销和对象重建后状态正确 |
| P3 游戏能力覆盖 | B10–B11、B13–B17 | 数据、游玩、视觉、输入、音频、内容与存储 | 各能力按 SPEC 独立验收；未验证能力仍返回明确原因 |
| P4 发布与更新演练 | B18 完整、B19 | 支持矩阵、性能基线、SDK 模板、可复现发布 | 一条命令构建；真实集成矩阵通过；旧插件兼容和更新失败回滚有证据 |

不预先承诺日期或“所有 Mod 都能做”。P0 未通过时，可以推进独立的契约设计与离线测试，但不得以新功能覆盖旧缺陷。每个任务交付独立可评审改动，不一次性建立大量空接口。

## Stakeholders

| 角色 | 负责 | 交付边界 |
|---|---|---|
| 你／底层维护者 | 架构决策、SDK 与版本政策、能力覆盖优先级 | 评审任务产物，不承担业务产品制作 |
| 实现者／编码模型 | 完成指定 B 任务、自动测试、安装和证据回写 | 无实测证据时明确保持未完成 |
| Mod 作者 | 用 SDK 制作实际功能，报告缺失能力 | 不向 Loader 塞入业务特例 |
| 游戏版本适配维护者 | 当前与新构建的符号、语义、能力支持表 | 把版本差异收敛在 Adapter/Runtime 边界 |

## Open Questions

- 哪些精确生命周期与判定方法可稳定接入，由 B01/B07 的本地证据决定；不能预设所有调用都经过 runtime_invoke。
- 音频跳转、进度重置和内容来源的实际约束，由 B11/B15 探测验证；不支持时细分能力，不伪造实现。
- 资源目标的稳定身份按实际加载机制逐类确定，实例 ID 不能直接当跨场景或跨版本标识。
- 其他注入器与其他游戏构建的兼容性只在拿到真实组合并通过测试后登记。这些是实施调查项，不阻塞写计划。
