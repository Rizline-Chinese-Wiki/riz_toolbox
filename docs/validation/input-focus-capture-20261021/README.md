# 输入采集与派发之间的焦点边界

2026-10-21，后续源码验证；未启动游戏。本目录不是 691 包的实机证据。

## 已复现问题

之前 after-input 采集只复制绑定与按键，直到 Host FrameUpdate 才查询文本编辑/模态焦点。按键在弹窗或编辑状态下被采集，若派发前弹窗关闭或编辑结束，就可能触发原本被挡住的快捷键。

`regression-before.log` 实际为 53/55：新增模态关闭与原生文本失焦两个场景均出现 Expected 0 / observed 1。首次运行碰到另一个代理尚未落盘的候选构造参数，编译失败原样保留为 `integration-before-contract.log`，不作为行为复现。

## 修复边界

- 在 after-input 采集阶段读取原生 EventSystem 焦点/UGUI 或 TMP 文本编辑状态，以及框架焦点栈和场景上下文，只为当时允许的动作保存边沿。
- Host 派发仍重新检查当前焦点、上下文和作用域。采集时允许不表示派发时可以绕过新弹窗。
- 原生控件回调在快捷键之前执行，因此在窗口回调之后重新核对动作代次，防止按钮回调重建动作后继承旧按键。
- Core broker 在每个动作回调前再次核对捕获的 owner、binding 与 epoch，防止同一批次早先回调把已有动作重绑到别人的旧按键。
- 原有三个参数的 Core Dispatch 入口保留，普通 SDK 没有新增强制成员。采集仍不执行插件动作，不持有 Unity 对象。

新增回归包括模态关闭、原生文本失焦、自有文本失焦、窗口焦点归还、后台按键、原生按钮回调替换动作、动作回调内重绑。已有当前焦点阻止、场景失效、已排空旧 epoch 和队列溢出测试保留。

`regression-first-attempt.log` 保存第一轮 54/55：自有文本焦点测试没有等待原有两帧激活请求结束，后续修正测试时序后 58/58；其后交叉审查补入同批回调重绑用例，最终59/59通过，结果见 `regression-after.log`；已随717包完整构建并安装。

这些是实际服务、Core broker、collector 与假原生后端的回归；原生焦点调用沿用已经接入的验证路径，尚须在新包实机确认。框架不消费游戏自己的输入，完整设备/模态/指针和场景矩阵仍未验收。
